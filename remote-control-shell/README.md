# Remote Control Shell（remote-control-shell）

Remote Control Shell は、セッションのヘッダーの「シェル」から右にパネルを開き、そのセッションのフォルダーでシェルのコマンドを実行するプラグインである。出力は、コマンドが動いているあいだから少しずつパネルに出る（出力をためるプログラムは「出力をためるプログラム」）。入力欄から「!」で送るコマンドと違って、コマンドは Claude が作業しているあいだもすぐに動き、その出力は Claude の会話に入らない。

この文書は、このプラグインの仕様である。プラグインの仕組みと API は、Gasho の [docs/plugins.md](https://github.com/4rtofl/Gasho/blob/main/docs/plugins.md) にある。いまのプラグインの API で作れる範囲に収め、Gasho の本体は変えない。`gasho-plugin.json` の `api` は、`ctx.dataDir` を使うので 1.1 にした。

## 決めたこと

1. キーを1つずつ送るターミナルではなく、コマンドを1つずつ実行するパネルにする。vim や top のように画面全体を使うプログラムと、パスワードの入力を待つプログラムは動かない（「コマンドを1つずつ実行するパネルにする」）
2. コマンドの記録と、コマンドを実行するフォルダー（作業フォルダー）は、セッションごとでなく、セッションのフォルダーごとに持つ（「記録はフォルダーごとに持つ」）
3. プラグインの更新、ホットリロード、gasho-daemon の再起動などでプラグインが止まるときは、実行中のコマンドも止める（「プラグインが止まるとき」）
4. ID とフォルダー名は `remote-control-shell` にする。`github` や `pondering` と同じく、ID がそのままフォルダー名になるので、`-plugin` は付けない。名前の Remote Control は、Claude Code の Remote Control（公式アプリからセッションにつなぐ機能）とは関係しない

## 「!」との違い

いまの Gasho では、入力欄で「!」から始まる文を送ると、Claude Code のシェルモードでコマンドが動く。Claude Code は、コマンドが終わってから、コマンドとその出力を会話に記録する。Gasho は、それを会話の中に出す（Gasho の `apps/web/src/lib/shell.ts`）。このプラグインは「!」と並べて使う。出力を Claude に読ませたいときは「!」を、読ませずに確かめたいときはこのパネルを使う。

| | 「!」 | このプラグイン |
|---|---|---|
| コマンドを実行するもの | Claude Code のシェルモード | daemon の部分が起動するシェル |
| 使えるセッション | Gasho から起動したセッション | gasho-daemon が見ているセッションすべて |
| Claude が作業しているとき | 送った指示と同じく、セッションが待機中になるまで待つ | すぐに実行する |
| 出力が画面に出るとき | コマンドが終わってから、まとめて | 実行中から少しずつ |
| 出力が Claude の会話に入るか | 入る | 入らない |
| 長い出力 | gasho-daemon が切り詰める | 1つのコマンドにつき 1MB まで残す（先頭から捨てる） |

## 方針

### コマンドを1つずつ実行するパネルにする

パネルは、入力したコマンドを1つずつ実行して、その出力を見せる。キーを1つずつ working server に送るターミナルにはしない。いまのプラグインの API では、次の点でターミナルを作りにくい。

- ターミナルには疑似端末（pty）が要る。Node.js では、ふつう node-pty のようなネイティブのモジュールで作る。daemon の部分は node_modules なしで動く1つのファイル（`daemon.js`）にビルドするので、これを入れられない
- キーを送るたびに `write` のメソッドを呼ぶことになり、操作のログがキーの数だけ増える
- daemon の部分から画面に知らせるイベント（docs/plugins.md の P8、API 1.5）は、同じ topic を1秒に1回までしか送らず、すべてのブラウザーに同じものを送る。キーを押すたびに変わる画面を届けるのには使えない

ターミナルにしないので、vim、top、less のように画面全体を使うプログラムと、パスワードなどの入力を待つプログラムは動かない。git や gh がページャーやエディターで止まらないよう、環境変数でそれらを使わないようにする（「コマンドの起動」）。

ターミナルが要るなら、Gasho の本体の機能にすることを提案する。gasho-daemon は、セッションの端末を動かすのに node-pty と xterm.js をすでに使っている（Gasho の `apps/daemon/src/terminal-host.ts`）。

### 記録はフォルダーごとに持つ

コマンドの記録と作業フォルダーは、セッションのフォルダーごとに持つ。記録には、コマンド、時刻、状態、出力を残す。同じフォルダーで作業するセッションは、同じ記録を見る。セッションを削除して同じフォルダーで起動し直したときや、フォークしたときも、動いているコマンドと記録がそのまま見える。セッションごとに持つと、セッションを削除したあとも動き続けるコマンド（開発用のサーバーなど）を、画面から止められなくなる。

### そのほかの方針

- コマンドを実行するのは daemon の部分だけにする。画面の部分が送るのは、コマンドの文字と、どのセッションかだけである。フォルダーは gasho-daemon が渡すセッションのフォルダー（`ctx.session`）から決め、ブラウザーからパスを受け取らない。Gasho の前提と同じである
- コマンド1つに、シェルを1つ起動する。`cd` で移った先は次のコマンドに引き継ぐ（「作業フォルダー」）。変数、alias、関数は引き継がない
- 出力は Claude の会話に入れない。Claude に渡すボタンは、段階2で足す（「実装の順序」）

## 画面

### ヘッダーの項目

セッションのヘッダーの「ファイル」（`order` は 400）の右に、「シェル」を出す。`order` は 450、アイコンは lucide の `SquareTerminal` にする。押すとシェルのパネル（`#/s/<working server>/<セッション>/p/remote-control-shell/shell`）を開き、開いているあいだは押した状態で出す。その working server で daemon の部分を使えないとき（`daemon.ready` が false）は出さない。

セッションのフォルダーで動いているコマンドがあれば、その数をバッジで出す。数は、`status` を10秒ごとに呼んで得る。

### パネル

PC ではセッションの右に、スマホではセッションの代わりに出す。どちらも Gasho のほかのパネルと同じで、枠は SDK の `Panel` を使う。

```
┌─────────────────────────────────────────────────────┐
│ シェル                              [記録を消す]  x │
│ ubuntu · /home/rg/repos/Gasho                       │
├─────────────────────────────────────────────────────┤
│ Gasho $ git status                        成功 0.3秒│
│ On branch main                                      │
│ nothing to commit, working tree clean               │
│                                                     │
│ Gasho $ npm test                  実行中 12秒 [停止]│
│ > gasho@0.1.0 test                                  │
│ ✔ tests 42                                          │
│                                                     │
├─────────────────────────────────────────────────────┤
│ Gasho/apps          [セッションのフォルダーに戻る]  │
│ $ コマンド（Enter で実行）                   [実行] │
└─────────────────────────────────────────────────────┘
```

パネルの見出しは「シェル」、副題は working server の名前とセッションのフォルダーである。中身は、上から古い順にコマンドを並べ、いちばん下に入力欄を置く。ターミナルと同じ並びにして、新しい出力が下に増えるようにする。パネルをいちばん下までスクロールしているときだけ、新しい出力に合わせて下までスクロールする。入力欄は、中身をスクロールしても下に残す。`Panel` の中身はスクロールする領域になっているので、その中で `position: sticky` を使って下に固定する。

見出しの右には「記録を消す」を置く。押すと、終わったコマンドの記録を消す。実行中のものは消さない。

### コマンドの表示

コマンドごとに、1行目に作業フォルダー、`$`、コマンド、状態を出し、その下に出力を出す。状態は次のように出す。

| 状態 | 出すもの |
|---|---|
| 実行中 | 経過時間と「停止」のボタン |
| 終わった（終了コード 0） | 成功の印と、かかった時間 |
| 終わった（0 以外） | 失敗の印、終了コード、かかった時間 |
| 止めた | 送った合図（SIGINT など）と、かかった時間。合図を送ったあとでも、コマンドが自分で終わったときは、終わったときと同じく終了コードを出す（「止める」） |
| 起動できなかった | 理由（シェルが見つからない、など） |
| プラグインが止まった | 「プラグインが止まったため終了」 |

経過時間は、working server とブラウザーの時計のずれを補って出す。

メニューには「もう一度実行」「入力欄に入れる」「コマンドをコピー」「出力をコピー」「この記録を消す」を置く。「もう一度実行」は、同じコマンドを、前に実行したフォルダーで実行する。「出力をコピー」は、残っている出力をすべて、色の指定を取り除いてコピーする。メニューを開いているときの Esc は、メニューだけを閉じる。

パネルを開いたときにすでに終わっていたコマンドは、出力の末尾20行だけを出し、「すべて表示（1,234 行）」で開く。パネルで動いているところを見たコマンドは、終わっても開いたままにし、20行より長ければ「末尾の 20 行だけにする」を出す。開いても、画面に出すのは末尾の2,000行までにして、それより前は「前を読む」で読む。実行中のコマンドも末尾の2,000行まで出し、それより前は「前の 2,000 行を表示」で出す。ブラウザーには実行中のコマンドの出力を512K文字まで置き、それより前は、コマンドが終わってから読む。行や文字が多いと、ブラウザーでの表示が遅くなるためである。

### 入力欄

- Enter で実行し、Shift+Enter で改行する。日本語を変換しているあいだの Enter では実行しない
- カーソルが先頭の行にあるときの↑と、末尾の行にあるときの↓で、このフォルダーで前に実行したコマンドを呼び出す
- 文字を選んでいないときの Ctrl+C で、いちばん新しい実行中のコマンドを止める
- Esc は、入力欄に文字があればそれを消す。空のときは、Gasho のパネルと同じくパネルを閉じる
- 入力欄の上に作業フォルダーを出す。セッションのフォルダーの外にいるときは色を変え、「セッションのフォルダーに戻る」を出す
- working server がオフラインのときと、daemon の部分を使えないときは、入力欄を使えなくし、その理由を出す

### スマホ

スマホでは、入力欄で、先頭の文字を自動で大文字にする機能、自動修正、スペルチェックを切る。Enter で実行し、改行は入れない。スマホのキーボードで打ちにくい記号のために、入力欄の上に `|`、`&&`、`>`、`~`、`/`、`-` のボタンと、前のコマンドを呼び出すボタン、「停止」のボタンを並べる。

### 出力の表示

出力は、標準出力と標準エラー出力を届いた順に1つにつなげ、等幅の文字で出す。ターミナルと同じく、2つを区別しない。既定では長い行を折り返す（設定の `wrap`）。

コマンドが ANSI エスケープシーケンスで指定した文字の色、背景、太字などは、そのとおりに出す。基本の16色は Gasho の明るいテーマと暗いテーマのそれぞれで読める色にし、256色と24ビットの色は指定のとおりに出す。行の先頭に戻す `\r` が来たら、その行をあとの文字で書き直す。進み具合を同じ行に書き直すプログラムのためである。カーソルを上の行に動かすものなど、ほかのエスケープシーケンスは取り除いて出す。そのため、何行もの表示を書き直す出力は、きれいには出ない。

出力は HTML として解釈しない。色ごとに分けた文字を、React の要素にして出す。

## daemon の部分

### コマンドの起動

`run` が呼ばれると、daemon の部分はコマンド1つにシェルを1つ起動し、状態が「実行中」の記録をすぐに返す。コマンドが終わるまでは待たない。`ctx.exec` は、コマンドが終わるまで出力を返さず、シェルも通さないので、このプラグインでは使わない。Node.js の `child_process.spawn` で起動する。

| 項目 | 内容 |
|---|---|
| シェル | 設定の `shell` で選ぶ。既定の `auto` は、環境変数 SHELL が bash、zsh、sh、dash、ksh ならそれを使い、それ以外（fish など）なら bash を使う |
| 起動のしかた | 設定の `startup` で選ぶ。既定はログインシェル（`-l`）で、`~/.profile` などを読む |
| コマンドの渡し方 | コマンドの文字は引数としてシェルに渡し、daemon の部分が用意した短いスクリプトの中の `eval` で実行する。複数行のコマンドもそのまま動く |
| 作業フォルダー | 「作業フォルダー」で決めたフォルダー |
| 標準入力 | `/dev/null`。入力を読むコマンドは、すぐに入力の終わりを受け取る |
| プロセスグループ | コマンドごとに新しく作る。止めるときは、グループ全体に合図を送る（`ctx.exec` と同じ）。スクリプトの初めの `set +m` で、シェルがコマンドを別のグループに入れないようにする。macOS の bash 3.2（`/bin/bash` と `/bin/sh`）は、対話シェル（`-i`）のとき、コマンドごとにグループを作るので、グループに送った合図がコマンドに届かなくなるためである |

gasho-daemon の環境変数のうち、シェルに引き継ぐのは HOME、USER、LOGNAME、PATH、SHELL、LANG、LC_ALL、XDG_RUNTIME_DIR、TMPDIR だけにする。gasho-daemon がセッションの端末に渡すものと同じである（Gasho の `apps/daemon/src/managed.ts` の `cleanEnv`）。`GASHO_HOOK_SECRET` のような gasho-daemon の設定の値は渡さない。そのうえで、次の値を足す。

| 環境変数 | 値 | 理由 |
|---|---|---|
| `TERM`、`COLORTERM` | `xterm-256color`、`truecolor` | 色を出せることを伝える（セッションの端末と同じ） |
| `FORCE_COLOR`、`CLICOLOR_FORCE` | `1` | 対応しているツールは、出力先がターミナルでなくても色を付ける |
| `PAGER`、`GIT_PAGER`、`GH_PAGER`、`MANPAGER` | `cat` | ページャーで止まらないようにする |
| `GIT_TERMINAL_PROMPT`、`GH_PROMPT_DISABLED` | `0`、`1` | 入力を待って止まらないようにする（`ctx.exec` と同じ） |
| `EDITOR`、`VISUAL`、`GIT_EDITOR` | `false` | エディターを開こうとするコマンド（メッセージを付けない `git commit` など）を、待たずに失敗させる |
| `PYTHONUNBUFFERED` | `1` | Python が出力をためずに書き出す（「出力をためるプログラム」） |
| `COLUMNS` | パネルの幅（文字数） | 幅に合わせて出力するツールのため |

### 作業フォルダー

最初の作業フォルダーは、セッションのフォルダーである。コマンドが `cd` で別のフォルダーに移って終わると、そのフォルダーを次のコマンドの作業フォルダーにする。コマンドを実行するスクリプトが、終わるときにいるフォルダーをファイルに書き、daemon の部分がそれを読む。

引き継ぐのは、最後に実行を始めたコマンドが、始めたときと違うフォルダーで終わったときだけにする。開発用のサーバーのように長く動くコマンドがあとから終わっても、そのあいだに移った作業フォルダーを上書きしない。「セッションのフォルダーに戻る」で戻したあとに終わったコマンドも、作業フォルダーを動かさない。「もう一度実行」は前に実行したフォルダーでコマンドを動かすが、そのコマンドが `cd` で移らない限り、作業フォルダーはそのままにする。

移る先は制限しない。シェルのコマンドはどこのファイルでも操作できるので、作業フォルダーだけを制限しても安全にはならない。セッションのフォルダーの外にいるときは、入力欄の上の表示の色を変え、「セッションのフォルダーに戻る」（`chdir`）を出す。作業フォルダーがなくなっていたときは、セッションのフォルダーで実行し、そのことを記録に添える。

### 出力の残し方

daemon の部分は、出力を UTF-8 の文字として読み、コマンドごとにためる。1つの文字を途中で分けることはしない。ためた量が設定の `maxOutputKB`（既定は 1024KB）を超えたら、先頭から捨てて末尾を残す。テストやビルドの結果は、出力の末尾に出ることが多いためである。捨てた量は記録に残し、画面は「先頭の N 文字は、残す量の上限を超えたので残っていません。」と出す。

出力の位置は、そのコマンドの出力の先頭からの文字数で表す。画面は受け取った位置を覚えておき、次はその続きだけを受け取る。

### 出力をためるプログラム

コマンドの出力先はパイプで、ターミナルではない。多くのプログラムは、出力先がターミナルでないと、出力をためておき、ある量になってから書き出す。daemon の部分は、Python がためないように `PYTHONUNBUFFERED=1` を渡す。Node.js、Go、Rust などは、出力先がパイプでも行ごとかすぐに書き出すので、そのまま少しずつ出る。

次のプログラムは出力をためるので、パネルには、ためた量がいっぱいになったときか、プログラムが終わったときにまとめて出る。

| プログラム | 少しずつ出す書き方 |
|---|---|
| C の標準入出力を使うもの（grep、sed、awk、jq など）。`tail -f app.log \| grep ERROR` の grep がこれにあたる | `grep --line-buffered`、`sed -u`、`jq --unbuffered`。awk は `fflush()` を呼ぶ。Linux では `stdbuf -oL grep ERROR` のように、`stdbuf -oL` を前に付けてもよい |
| Ruby、Perl | スクリプトの中で `$stdout.sync = true`（Ruby）、`$\| = 1`（Perl）とする |

ためた出力は、書き出す前にプログラムが「停止」や「強制終了」で止まると、パネルに出ないまま消える。

どのプログラムにもターミナルと同じく書き出させるには、疑似端末（pty）が要る。「コマンドを1つずつ実行するパネルにする」に書いた理由で、このプラグインでは作らない。`stdbuf` と同じ環境変数（`LD_PRELOAD`）をすべてのコマンドに渡す形も考えたが、ファイルに書く出力（`sort big.txt > out.txt` など）まで1行ずつ書き出して遅くなり、macOS では効かないので、採らなかった。

### 止める

「停止」は、コマンドのプロセスグループに SIGINT を送る。ターミナルで Ctrl+C を押したときと同じ合図である。3秒たっても終わらなければボタンが「強制終了」に変わり、押すと SIGKILL を送る。ホットリロードのあいだ、古い版が動かしているコマンドには、そのシェルが起動したときと同じプロセスだと確かめられたときだけ送る（「プラグインが止まるとき」）。

SIGINT はシェルにも届く。そのままでは、zsh はコマンドを待たずにすぐ終わり、bash の対話シェルは終了コード 1 で終わるので、コマンドがどう終わったかが分からない。そこで、コマンドを実行するスクリプトで `trap 'exit $?' INT TERM` とし、シェルはコマンドが終わるのを待ってから、コマンドの終了コードで終わる。SIGTERM（「プラグインが止まるとき」）にも同じ trap を置くのは、対話シェルが SIGTERM を受けても終わらず、`;` や改行のあとのコマンドに進むためである。trap が無いと、`npm run build; npm run deploy` の実行中にプラグインが止まったとき、止まるはずの `deploy` が動き出す。合図で止まったコマンドの終了コードは 128 + 合図の番号（SIGINT なら 130）なので、送った合図のこの値のときは「止めた」にし、ほかの値のときは、コマンドが自分で終わったものとして終了コードを出す。このプロセスが合図を送っていないときは、trap で受ける SIGINT と SIGTERM の値（130 と 143）を「止めた」にする。ホットリロードのあいだに、新しい版が古い版のコマンドを止めたときや、`kill` で外からグループに送ったときである。そのため、合図を受けずに自分で `exit 130` で終わったコマンドも「止めた」と出る。どの合図で止まったかをシェルがファイルに書き残せば分けられるが、終わり方を決める処理が、そのファイルを読むまで待つことになるので、採らなかった。SIGINT を受けて自分で `exit 1` で終わるコマンドは「終了コード 1」になる。`while` の繰り返しのように、シェルが次のコマンドを起動するあいだに合図が届いたときは、その前のコマンドの終了コード（多くは 0）になる。

時間の上限は付けない。開発用のサーバーのように、動かし続けるコマンドがあるためである。そのかわり、同時に動かせるコマンドは、1つのフォルダーで4つ、1つの working server で16までにする。超えたときは実行せず、ほかのコマンドを止めてから実行するように知らせる。

### プラグインが止まるとき

daemon の部分は、プラグインを更新したとき、ホットリロードしたとき、無効にしたとき、gasho-daemon が止まるときに止まり、そのまえに `stop` が呼ばれる。`stop` では、実行中のコマンドに SIGTERM を送り、2秒たっても残っているものには SIGKILL を送る。シェルは、SIGTERM で止まったコマンドのあとのコマンドを実行せずに終わる（「止める」）。gasho-daemon は `stop` を5秒まで待つので、5秒以内に終える。止めたコマンドの記録は「プラグインが止まったため終了」にする。ホットリロードのときも、新しい版は、古い版で動いていたコマンドを引き継がない。

gasho-daemon が `stop` を呼ばずに止まったとき（4rtofl/Gasho#128）と、daemon の部分が落ちたときは、記録が「実行中」のまま残る。この記録は、次にそのフォルダーの記録を読んだ daemon の部分が閉じる。PID は、そのプロセスが終わるとほかのプロセスに使われるので、記録には、daemon の部分のプロセスとシェル（プロセスグループの先頭）の PID とともに、それぞれが起動した時刻を残す。PID と起動した時刻の両方が今のプロセスと合うときだけ、記録を書いたときと同じプロセスとみなす。

- daemon の部分のプロセスが同じものなら、そのプロセスが記録を書くのを待つ（ホットリロードで、古い版が止まるまで）
- 同じものでなければ、記録を「プラグインが止まったため終了」にする。シェルが同じものなら、そのプロセスグループに SIGKILL を送る。同じものと確かめられなければ、何も送らない。PID を使い回した、同じユーザーの無関係なプロセスグループ（macOS の GUI のアプリなど）を止めないためである

確かめられないのは、シェルが先に終わって、`&` で動かしたものだけが残っているときと、起動した時刻を残す前の版の記録である。これらのコマンドは動き続けることがあるので、`ps` などで探して止める。起動した時刻は、Linux では `/proc/<PID>/stat` と起動ごとの ID（`/proc/sys/kernel/random/boot_id`）から、macOS などでは `ps -o lstart=` で読む。

コマンドを止めずに残し、新しい版が引き継ぐ形も考えた。しかし、systemd で動かしている gasho-daemon を止めると、systemd はそのサービスから起動したプロセスをすべて止める。Gasho がセッションの端末を別の systemd のスコープで動かすのも、このためである（Gasho の `apps/daemon/src/managed.ts` の `scopeArgs`）。引き継げるのがホットリロードのときだけになるので、採らなかった。

### 記録の保存

記録は、`ctx.dataDir` にフォルダーごとに保存する。プラグインや gasho-daemon が起動し直しても、記録と作業フォルダーは残る。

```
~/.local/share/gasho/plugin-data/remote-control-shell/
└─ folders/<セッションのフォルダーのパスの SHA-256 の先頭16文字>/
   ├─ folder.json       セッションのフォルダーのパス、作業フォルダー、セッションのフォルダーが無いと気づいた時刻
   ├─ <記録の ID>.json   コマンド、実行したフォルダー、始めた時刻、終わった時刻、状態、終了コード、
   │                     daemon の部分のプロセスとシェルの PID と起動した時刻
   └─ <記録の ID>.log    出力（上限まで。末尾を残す）
```

記録は、フォルダーごとに新しいものから50件（設定の `keepJobs`）を残し、それより古いものを消す。実行中の出力も数秒ごとに書き出すので、daemon の部分が急に落ちても、そこまでの出力は残る。

worktree を片付けたときのように、セッションのフォルダーが無くなったら、その記録は画面から消せない。daemon の部分は、起動したときと6時間ごとに、セッションのフォルダーがあるかを見る。無ければ、そのことに最初に気づいた時刻を `folder.json` に残し、そこから7日たったら、記録と出力ごと消す。そのまえにフォルダーがあると分かれば、残した時刻を消す。外付けのディスクやネットワークのドライブがつながっていないあいだに起動しても、すぐには消さないためである。この daemon の部分で実行中のコマンドがあるフォルダーは消さない。フォルダーは gasho-daemon を動かしているユーザーだけが開けるようにし（700）、ファイルもそのユーザーだけが読み書きできるようにする（600）。

## 出力は変化を待つ呼び出しで届ける

出力は、画面のほうから daemon の部分を呼んで受け取る。daemon の部分から画面に知らせるイベント（P8）は API 1.5 で入ったが、すべてのブラウザーに同じものを送り、同じ topic は1秒に1回までしか送らない。docs/plugins.md も、コマンドの出力のように1秒に何度も届けたいものは、呼び出し（P7）で読むとしている。呼び出しで読めば、API 1.1 の gasho-daemon でも動く。ただし、`useRequest` は引数ごとに結果を覚えておく。出力の位置を引数に入れると、呼ぶたびに覚えておく結果が増え、入れなければ毎回すべての出力を受け取ることになる。

そこで、画面は `useCall` で `watch` を呼び、daemon の部分は、変化があるまで待ってから答える。

```
  パネル                       Gasho サーバー、gasho-daemon       daemon の部分
    │ watch（変化の番号 12、npm test の出力は 3,200 文字目まで受け取った）
    │────────────────────────────────▶│─────────────────────────────▶│ 変化を20秒まで待つ
    │                                 │                              │ npm test が出力した
    │◀────────────────────────────────│◀─────────────────────────────│ 3,200 文字目からあとを返す
    │ 0.2秒あけて、次の watch         │                              │
```

`watch` の引数は、前に受け取った変化の番号と、追っているコマンドごとの出力の位置である。daemon の部分は、記録の一覧が変わったとき（コマンドが始まった、終わった、作業フォルダーが変わった）と、追っているコマンドの出力が増えたときに、すぐ答える。1回に返す出力は256KBまでにし、残りは次の呼び出しで返す。20秒たっても変化がなければ、変化なしと答える。変化の番号は、daemon の部分が起動し直すと振り直すので、番号が合わないときは記録の一覧をすべて返す。

画面は、答えを受け取るとすぐに次の `watch` を呼ぶ。出力が続くときは、前の呼び出しから0.2秒あける。パネルを開いたときは、まず記録の一覧を受け取り、画面に出すコマンドの出力の末尾を、続く `watch` で受け取る。

gasho-daemon は、1つのプラグインの呼び出しを同時に8つまで動かし、それを超えた分は待たせる。待っている `watch` が8つの枠を埋めると、`run` や「停止」が待たされる。そのため、daemon の部分は待たせる `watch` を4つまでにし、それを超えた `watch` には待たずに答える。画面は2秒あけて呼び直す。

パネルを閉じたときと、ページが見えていないとき（スマホでほかのアプリを開いているときなど）は `watch` を止め、戻ったら続きから受け取る。Gasho サーバーとの接続が切れて呼び出しが失敗したときは、1秒、2秒、5秒とあけて呼び直す。受け取った記録と出力は `usePluginState` に置き、パネルを開き直したときやホットリロードのあとに、読み直さずに出せるようにする。

## メソッド

| メソッド | 種類 | 待つ時間 | 引数 | 返すもの |
|---|---|---|---|---|
| `run` | write | 15秒 | `command`（16,000文字まで）か `again`（もう一度実行する記録の ID）、`cols`（パネルの幅）、`request`（画面が付ける依頼の番号。16桁の16進数） | 始めたコマンドの記録。同じ `request` の記録がすでにあれば、実行せずにその記録に `earlier: true` を付けたもの |
| `signal` | write | 10秒 | `job`（記録の ID）、`signal`（`INT` か `KILL`） | その記録 |
| `chdir` | write | 10秒 | `repo`（なければセッションのフォルダー） | 新しい作業フォルダー |
| `clear` | write | 10秒 | `job`（なければ、終わった記録すべて） | 消した数 |
| `watch` | read | 30秒 | `since`（変化の番号）、`offsets`（記録ごとの出力の位置）、`waitMs`（20,000まで） | 変化の番号、作業フォルダー、ホームフォルダー（表示で `~` にする）、working server の時刻、記録の一覧、増えた出力 |
| `output` | read | 15秒 | `job`、`from`、`limit` | 出力の一部。「すべて表示」と「前を読む」に使う |
| `status` | read | 10秒 | なし | 実行中のコマンドの数（バッジ） |

どのメソッドも、呼び出しでセッションを指定する。daemon の部分は、そのセッションのフォルダー（`ctx.session.cwd`）の記録を扱う。`chdir` の `repo` は、gasho-daemon がセッションのフォルダーの中で見つけたリポジトリのパスだけを受け付ける（`ctx.session.repo()`）。`run` の `again` では、daemon の部分が覚えている記録から、コマンドと実行したフォルダーを使う。どちらも、ブラウザーからパスを受け取らないためである。

`run` の答えが待つ時間までに来ないと（「working server から応答がありません。」など）、または答えの前に working server との接続が切れると（「working server との接続が切れました。」）、daemon の部分がコマンドを実行したかどうかは、画面からは分からない。gasho-daemon が混んでいるときは、答えが届かなかったあとで実行されることもある。そこで、画面は `run` ごとに依頼の番号を付け、daemon の部分は、記録にその番号を残す。答えが来なかったときは、同じ番号で2回まで送り直す。実行されていれば、daemon の部分はその記録を返し、二重には実行しない。それでも答えが来なければ、入力欄にコマンドを残し、同じコマンドをもう一度実行すると同じ番号で送る。前の記録が返ったとき（`earlier`）は、前に送ったときに実行されていたことを入力欄の下に出し、入力欄にコマンドを残す。時間切れのあとでコマンドが実行されて終わり、あとで同じコマンドを実行し直そうとしたときに、実行しなかったことが分かるようにするためである。もう一度送ると、新しい番号で実行する。送り直した `run` も、操作のログに残る。

`write` のメソッドは、Gasho サーバーが操作のログに残す。`run` の要約には、コマンドの1行目を `$ npm test` の形で入れる。Gasho サーバーは要約を300文字で切る。設定の `logCommands` を切ると、要約は「コマンドを実行」だけにする。

記録は、次の形で画面に渡す。

```ts
/** 1つのコマンドの記録 */
export interface ShellJob {
  id: string;
  command: string;
  /** 実行したフォルダー（絶対パス） */
  cwd: string;
  /** ミリ秒（working server の時計） */
  startedAt: number;
  endedAt?: number;
  state: "running" | "exited" | "stopped" | "failed" | "lost";
  exitCode?: number;
  /** stopped のとき、送った合図（"SIGINT" など） */
  signal?: string;
  /** failed の理由や、作業フォルダーがなかったときの断り書き */
  note?: string;
  /** 出力の文字数、上限を超えて先頭から捨てた文字数、出力の行数 */
  size: number;
  dropped: number;
  lines: number;
}
```

## 設定

`server` の設定は、すべてのブラウザーで共通で、daemon の部分にも渡る（`ctx.settings`）。

| キー | 種類 | 保存先 | 既定 | 内容 |
|---|---|---|---|---|
| `shell` | select | server | `auto` | 使うシェル。`auto`、`bash`、`zsh`、`sh` から選ぶ |
| `startup` | select | server | `login` | シェルの起動のしかた。`login` は `-l` を付ける。`interactive` は `-i` を付け、alias を使えるが、ターミナルがないという警告が出ることがある。`plain` はどちらも付けない |
| `maxOutputKB` | number | server | 1024 | 1つのコマンドで残す出力（64〜8192） |
| `keepJobs` | number | server | 50 | フォルダーごとに残す記録の数（10〜500） |
| `logCommands` | boolean | server | true | 操作のログに、実行したコマンドの文字を残す |
| `wrap` | boolean | browser | true | 出力の長い行を折り返す |

## 安全

- このプラグインを入れると、Gasho を開ける人は、daemon の部分を動かす working server で、gasho-daemon を動かしているユーザーとして、どのコマンドでも実行できる。「!」でも同じことができるが、「!」を使えるのは Gasho から起動したセッションだけである。このプラグインは、gasho-daemon が見ているセッションすべてで使える。daemon の部分を動かす working server は、プラグインの画面で選べる（docs/plugins.md の P9）
- シェルに渡す環境変数は、「コマンドの起動」に書いたものだけである。`GASHO_HOOK_SECRET` のような gasho-daemon の設定の値は、シェルに渡らない。ただし、シェルはそのユーザーのファイルを読めるので、gasho-daemon のトークンを書いたファイル（`~/.config/gasho/daemon.json`）も読める。「!」でも同じである
- `run`、`signal`、`chdir`、`clear` は `write` のメソッドなので、操作した端末、プラグイン、working server、セッションとともに、操作のログに残る。コマンドに秘密の値を書くと、それも操作のログに残る。残したくないときは、設定の `logCommands` を切る
- 出力は、working server の `ctx.dataDir` に保存する。秘密の値を出力したときは、「記録を消す」か、その記録のメニューの「この記録を消す」で消す
- 出力は HTML として解釈しない（「出力の表示」）

## 実装の順序

段階1（この版）では、この文書の「画面」から「設定」までを作った。段階2では、次のものを足す。

- 実行中のコマンドに、1行ずつ入力を送る（y/n の確認に答えるなど）。標準入力をパイプにする
- 「Claude に渡す」。コマンドと出力の末尾を、セッションへの発言として送る。SDK の `useSendInput` を使うので、権限 `session.input` が要り、Gasho から起動したセッションでだけ使える
- working server で動いているコマンドの一覧（ホームのタイル）。セッションがなくなったフォルダーのコマンドも、ここから止められるようにする
- よく使うコマンドを1回で実行するボタンと、フォルダーの中のリポジトリに移るボタン（`chdir` の `repo`）

## 今回は扱わないこと

- キーを1つずつ送るターミナル（「コマンドを1つずつ実行するパネルにする」）
- コマンドをまたいで、変数、alias、関数を引き継ぐこと
- Tab での補完
- セッションのないフォルダーでシェルを開くこと
